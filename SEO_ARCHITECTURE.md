# X-GU.RU — как работают тысячи SEO-страниц

Этот документ описывает именно programmatic SEO-модель x-gu.ru: какие URL физически существуют, какие должны индексироваться и почему число сгенерированных файлов нельзя путать с числом страниц, которые стоит отдавать поиску.

## 1. Исторический масштаб

В сохранённом `server-opt/seo_report.py` зафиксирована исходная точка перед первым shrink:

- sitemap: **37 625 URL**;
- после shrink: **1 097 URL**;
- Яндекс на тот момент показывал в поиске только **41 URL**.

Это важный сигнал: сама возможность сгенерировать десятки тысяч URL не означает, что поисковику нужны десятки тысяч URL.

Текущий исторический baseline `server-opt/index_policy.baseline.json` содержит:

- 57 открытых городов;
- 18 открытых услуг.

Старая policy-модель открывает их декартово произведение:

```text
57 × 18 = 1 026 city/service landing pages
+ 57 city hubs
+ homepage
+ /privacy/
+ 12 search-protected URLs outside the standard matrix
= 1 097 sitemap URLs
```

В историческом `server-opt/whitelist.txt` 41 URL. 29 из них уже входят в стандартное ядро, 12 добавляются поверх него.

## 2. Физическая страница != индексируемая страница

Generator может иметь десятки тысяч физических каталогов вида:

```text
/<city>/<service>/index.html
```

Но release policy решает, должна ли конкретная страница участвовать в поиске.

Для закрытой страницы нормальный жизненный цикл:

```text
файл существует
→ meta robots = noindex
→ URL отсутствует в sitemap
→ открытые хабы/главная на него не ссылаются
→ после проверки поисковых данных страницу при необходимости можно purge/remove
```

Для открытой страницы:

```text
index,follow
→ canonical на саму себя
→ присутствует в sitemap
→ имеет входящие crawlable ссылки с индексируемых страниц
→ проходит quality/uniqueness checks
```

## 3. Что делает release policy сейчас

Release содержит:

```text
.xgu-index-keep.json
.xgu-whitelist.txt
```

`open_cities` и `open_services` задают основное индексируемое ядро. Whitelist сохраняет URL, которые нельзя закрыть общей матрицей — например страницу, уже найденную поиском.

`server-opt/shrink_index.py`:

1. читает reviewed policy;
2. читает source whitelist;
3. рассчитывает набор URL, которые должны остаться открытыми;
4. ставит `noindex` остальным страницам;
5. возвращает `index` страницам, которые снова открыты;
6. пересобирает sitemap только из разрешённых URL;
7. сохраняет policy и whitelist snapshot внутрь release.

## 4. Почему 37 625 страниц были опаснее 1 097

Основные риски массового city/service генератора:

- десятки страниц отличаются только названием города/услуги;
- поисковый спрос есть не для каждой пары `город × услуга`;
- слабые страницы разбавляют сильные;
- поисковые роботы тратят обход на URL, которые не имеют ценности;
- страницы могут конкурировать друг с другом по близким интентам;
- массовая шаблонность может выглядеть как doorway/scaled content.

Поэтому цель проекта — не «проиндексировать максимум». Цель — **оставлять в индексе максимум страниц, у которых есть отдельный интент, спрос и полезность**.

## 5. Главный оставшийся недостаток baseline v1

Сейчас policy в основном работает как матрица:

```text
город открыт + услуга открыта = комбинация открыта
```

Например, если в policy есть 57 городов и 18 услуг, она автоматически считает потенциально индексируемыми все 1 026 комбинаций.

Это слишком грубо.

Целевая модель должна работать на уровне пары:

```text
moskva/prodvizhenie-saita              OPEN
moskva/seo-audit-saita                 OPEN
tula/prodvizhenie-saita                OPEN
tula/audit-povedencheskikh-faktorov    CLOSED
...
```

Иными словами, следующий policy version должен поддерживать **explicit city/service pairs**, а не только cross-product.

## 6. На основании чего открывать конкретную пару

Страница `/<city>/<service>/` должна получать `index` только при достаточных доказательствах. Источники сигналов:

### Search evidence

- URL уже находится в поиске Яндекса;
- Google Search Console показывает impressions/clicks;
- есть запросы с реальным спросом;
- страница имеет исторический трафик/лиды/внешние ссылки.

### Page quality

- уникальные Title/H1/Description;
- достаточный полезный видимый контент;
- нет почти полного дубля другой city/service страницы;
- контент отвечает именно локальному/сервисному интенту, а не просто меняет город в шаблоне;
- нет фиктивных отзывов, рейтингов и KPI;
- корректная structured data.

### Internal graph

- индексируемая страница имеет входящую ссылку с индексируемого хаба/страницы;
- открытая страница не должна массово ссылаться на закрытые `noindex` URL;
- city hub должен вести только на реально открытые для этого города service pages;
- sitemap должен содержать только канонические индексируемые URL.

## 7. Аудит полного индексируемого корпуса

Использовать новый инструмент:

```bash
python server-opt/programmatic_seo_audit.py \
  --root /var/www/x-gu.ru/current \
  --json-out /tmp/xgu-programmatic-seo.json
```

Он анализирует **весь release**, но quality-метрики считает прежде всего по страницам, которые policy считает индексируемыми.

Показывает:

- physical pages;
- indexable pages;
- policy-closed pages;
- типы открытых страниц;
- индексируемые страницы с недостаточным объёмом текста;
- индексируемые страницы без входящих внутренних ссылок;
- ссылки `open → closed`;
- точные дубли видимого текста;
- почти-дубли по SimHash.

Строгий режим:

```bash
python server-opt/programmatic_seo_audit.py \
  --root /var/www/x-gu.ru/current \
  --strict \
  --max-thin 0 \
  --max-orphans 0 \
  --max-links-to-closed 0
```

Near-duplicate threshold пока рекомендуется использовать как отчётный сигнал до получения baseline на реальном production release. Не надо автоматически закрывать страницу только потому, что SimHash считает её похожей.

## 8. Search Console и Яндекс должны управлять ядром ДО shrink

В репозитории есть два исторических инструмента:

- `server-opt/build_whitelist.py` — получал страницы из Яндекс Вебмастера;
- `server-opt/gsc_audit_noindex.py` — уже после shrink проверял, не закрыли ли страницу, имевшую показы в Google.

Это правильные источники, но исторический workflow был перевёрнут: Google evidence проверялся после закрытия.

Целевая схема:

```text
Yandex evidence
       +
Google Search Console evidence
       +
manual/business protected URLs
       ↓
search evidence dataset
       ↓
reviewed pair-level index policy
       ↓
shrink candidate
       ↓
full programmatic SEO audit
       ↓
predeploy
```

То есть сначала данные поисковиков, потом решение `index/noindex`, а не наоборот.

## 9. Что считать успехом

Не количество созданных страниц.

Главные показатели по каждому cohort/page type:

- сколько URL открыто для индекса;
- сколько реально searchable/indexed;
- сколько имеют impressions;
- сколько имеют clicks;
- median position;
- доля страниц с 0 impressions за 28/90 дней;
- доля near-duplicate pages;
- количество orphan pages;
- количество open→closed links;
- leads/conversions на landing page;
- число страниц, которые поисковик исключил как low-value / duplicate / crawled-not-indexed.

## 10. Практический принцип x-gu.ru

**Генерировать можно десятки тысяч страниц. Индексировать нужно только те, для которых мы можем доказать отдельную поисковую ценность.**

Следующее крупное SEO-изменение после получения production-аудита — policy v2 с explicit `city/service` pairs и построением этой policy из объединённых данных Яндекс Вебмастера + Google Search Console.
